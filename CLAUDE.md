# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The Next.js site in `web/` — https://aeroallocator.app, the **sAERO allocator**: which Aero gauges pay the most per day for an amount, the owner's sAERO positions, allocate (across chains too) and return-to-idle from the wallet, plus free and paid (x402) APIs for agents. Aero replaced weekly voting with continuous sAERO allocation on 2026-10-22 and Velodrome merged into it, so the weekly-vote dashboard, its APIs and schedules were removed from `web/` and CI on 2026-10-24, and the weekly-vote MCP engine that lived in `src/` (forecasts, bribe and vote tools, backtest scripts) was removed on 2026-10-28; it is in git history, last present at commit `1f94d77`. The root keeps only `skills/` (two agent skills with their tests), `scripts/audit-gate.ts` (CI) and docs. It never holds keys; the allocate flow signs in the user's own wallet. `README.md` leads with the site (APIs, env vars, deploy, how history is kept, the agent skills and the paid API).

## Commands

Root (Node 22; only the skills' tests and the audit gate live here):

```bash
npm run typecheck                  # tsc --noEmit over scripts/
npm test                           # vitest run: skills/**/*.test.mjs and scripts/*.test.ts
npm run build                      # a deliberate no-op: the Vercel project still runs the root build first (see README, Deploying)
```

`web/` (separate `package.json` and lockfile; run from `web/`): `npm run dev`, `npm test`, `npm run lint`, `npx tsc --noEmit`, `npm run build`. Lint is ESLint 9 with `eslint-config-next` (flat config in `web/eslint.config.mjs`; Next 16 removed `next lint`); CI fails on errors only, and `react-hooks/set-state-in-effect` is a warning because the page uses the mounted-state pattern on purpose.

CI also runs `npx tsx scripts/audit-gate.ts .` and `... web`: `npm audit --omit=dev` must report nothing except the accepted advisory listed in `scripts/audit-gate.ts` (the zod one, which reaches 20+ packages in `web/`); any other advisory, or an audit that can't run, fails the job. Run it locally the same way, and delete an `ACCEPTED` entry once the audit stops reporting it. Each accepted advisory also has a date in `ACCEPTED_UNTIL` (zod: 2026-11-30); past it the gate fails again until someone re-checks upstream and either fixes it or moves the date.

Before proposing a push or deploy, use the `verify` skill (typecheck/test/build for both packages in order, secret scan, audit). CI (`.github/workflows/ci.yml`) runs the same sequence.

## Architecture

- **`web/` is Aero on Base plus six more chains** (`web/lib/protocol.ts`, `web/lib/aero-chains.ts`). The wallet flow's contract addresses are in `web/lib/saero.ts`. USD prices come from `web/lib/prices.ts` (DefiLlama, with a stale fallback) and the node URLs from `web/lib/rpc-config.ts`; both used to come from the removed engine. The live allocate flow is `web/lib/allocate.ts` (`allocate()` on Aero's Voter).
- **Web API** (`web/app/api/*`): `gauges` (gauge list per Aero chain), `gauge-fees` (+ `gauge-fees/ingest`, run by the seven Vercel Crons in `web/vercel.json`, which keep the per-chain fee ledger in a Blob), Arc (5042) is the seventh chain, added 2026-10-28: reads go through publicnode, Tenderly's gateway and dRPC (Circle's own `rpc.mainnet.arc.io` refused requests from here with a Cloudflare 1009), logs only through Tenderly's gateway (100,000 blocks a query; dRPC's free tier, publicnode and thirdweb can't serve them), and viem's Arc definition has no Multicall3 so `aero-chains.ts` declares the standard address; a fork test of the allocate-across-chains flow with Arc as a target succeeded (25.5 power on Arc, quote refunded); `gauge-flows` (which gauges are gaining or losing share of the allocation weight, from a snapshot of every gauge's weight and incentives that the same ingest crons store every 30 min in a Blob, `web/lib/weight-history*.ts`; also lists gauges whose incentives appeared inside the window, and only when an earlier snapshot recorded them as none; empty until two hours of snapshots exist), `gauge-history` (one gauge's fees released per 6 h from the fee ledger, its weight snapshots and its steadiness, for the chart under a table row; `web/lib/fee-history.ts`; steadiness = complete 12 h stretches that paid at least half the average, over the 4 days the ledger keeps, and is also added to `gauge-fees` as `steady`; the table's Steady column shows "incentives" instead when incentives are at least half of a gauge's income, `steadyLabel` in `web/lib/gauge-yield.ts`, because incentives stream at a fixed rate while fee releases are lumpy), a daily record kept 90 days per chain (`gauge-daily-history-{chainId}.json`, `web/lib/daily-history*.ts`): the same ingest crons add each finished UTC day once, with the fees each gauge released that day (a gauge's first release in the record is left out, as in the fee pace; `seen` remembers it), its weight and its incentives at the last snapshot of the day; `gauge-history` returns it as `daily` and the chart draws it from two days on (it is the only history that can't be rebuilt from the chain, so never reset it), `allocation-fee` (read-only live quote of the ETH an allocation to another chain needs), `all-chains-split` (the best split of an amount over every chain at once, `web/lib/all-chains-split.ts` + `all-chains-read.ts`: every set of chains is tried at its best split and the set with the most net of each extra chain's one-off ETH fee over the horizon wins, Base alone returned for comparison; fees come from a two-point straight-line model of the adapter quote for the search and an exact `quoteCrossChain` re-quote for the chosen chains; read-only, the page's "compare all chains" panel), the allocate-across-chains flow (`web/lib/allocate-multichain.ts`, `web/app/saero-allocate-chains.tsx`; see the sAERO paragraph below), `token-prices` (USD prices for up to 12 Base token addresses, so the page can value a position's earned fees in the browser without sending the position anywhere), the paid x402 routes `v1/position`, `v1/allocate-plan` and `v1/cross-chain-plan` (handlers in `web/lib/v1-position.ts` / `v1-allocate-plan.ts` / `v1-cross-chain-plan.ts`, wiring in `web/lib/x402.ts`; the cross-chain one ($0.25) runs `planAcrossChains` server-side from the position's state on every chain, with `chains=5042:30,10:20` or the best split from `readAllChainsSplit`, simulates only step 1 (`simulateStep`), reports each step's `blockedBy` from the chains' waits and in-flight checks, and can take ~20 s cold because it reads seven chains, so keep `maxDuration` at 60; they serve 501 unless `X402_PAYTO_ADDRESS`, `CDP_API_KEY_ID` and `CDP_API_KEY_SECRET` are all set; keep new paid routes to answers the free reads can't give, and validate input with a 400 before any read so a bad call is never charged), and `share` (the sAERO share card; a position's "share card" button builds its link from the power rounded to two figures plus the theme, only when pressed, and never the token id, address, current gauges or staying cost; bump `SHARE_CARD_VERSION` in `web/lib/site.ts` when the card changes so link previews refetch it). Verify data-backed changes through the running dev server. `/llms.txt` (`web/lib/llms-txt.ts`) describes the free and paid endpoints for agents; keep its prices tied to the route constants. Skills install straight from this public repo with `npx skills add Hryhorii77/aero-allocator [--full-depth --skill <name>]` (a root SKILL.md hides the folders under `skills/` unless `--full-depth` is passed); each SKILL.md's front matter must be valid YAML (the `description` is quoted because it holds ": "), which `skills/frontmatter.test.mjs` checks. `skills/veaero-to-saero-upgrade/` is the companion agent skill for the veAERO to sAERO upgrade (read-only checker `scripts/check.mjs` plus the rules and calldata in `scripts/upgrade.mjs`; contract facts in the skill's SKILL.md, taken from Aero's metadex-public repo and a Base fork test); its tests compare every selector and the calldata with viem. `skills/saero-allocator-automator/` is an agent skill (SKILL.md plus dependency-free `scripts/decide.mjs`, tested by `decide.test.mjs` through the root vitest config, and `scripts/run.mjs`) that decides when to re-allocate and checks an `allocate-plan` before handing it to the owner's wallet; keep its rules in step with the advice rules in `web/lib/position-advice.ts`. `/openapi.json` (`web/lib/openapi.ts`, OpenAPI 3.1, required by Circle's Agent Marketplace listing) describes the same routes with real parameters, response schemas and the 402 behaviour; prices come from the route constants and `v1-handlers.test.ts` fails if a paid response gains a field the schema doesn't list, so update `openapi.ts` whenever a route's parameters or response change. `vitest.config.mts` inlines `@x402/next` so tests can run the real payment flow with a stub facilitator.
- Address lookup reads the owner's sAERO positions in the browser, so the address never reaches the server. The "remind me" link on a waiting position builds a calendar `.ics` file in the browser (`web/lib/ics.ts`); keep any reminder feature client-side for the same reason. The wait length is read from the Base leaf voter's `allocationCooldown` by `readGauges` and returned as `cooldownSec` on the Base `/api/gauges` list (the other chains' lists omit it), so the allocate panel, the advice line, the best-split card and the paid API all use the live value; 169,200 s (`DEFAULT_COOLDOWN_SEC`) is only the fallback, and `waitHours` turns it into the hours the texts say (static explanatory copy still says 47). The 47 h wait is per position (leaf `tokenStates(tokenId)`): a never-allocated position simulates an allocation cleanly, and Aero's escrow has `createStake` but no split or merge function (checked on Base 2026-10-26). Aero's Autopilot (docs: app.aero.xyz/docs/features/autopilot) pools deposits in its own position and leaves the depositor's original sAERO NFT at zero balance as the withdrawal key, so a position with `staked == 0` is shown with a note and no allocate buttons. 62 such zero-amount NFTs existed on 2026-10-26; the chain alone can't say which are Autopilot keys and which are emptied stakes, so the note says "if". Aero's contract source is public at github.com/dromos-labs/metadex-public (V3/src: `voter/LeafVoter.sol`, `rewards/VotingRewardsManager.sol`); a position's unclaimed fees are `earnedFees(tokenId, maxCheckpoints)` on each current gauge's rewards manager (`registry.gaugeToRewards(gauge)`), read in `web/app/earned-fees.tsx` (fees only; incentives are per program and not read). Each position card also shows what staying costs per day (`web/app/position-advice-line.tsx`, `web/lib/opportunity.ts`), from the same `analysePosition` the paid API and the allocate panel use; it fetches only the public `/api/gauges` and `/api/gauge-fees`, so nothing about the position leaves the browser. The positions panel reads the connected wallet on connect (once per address, in the browser). The best-split card shows a range from `web/lib/projection.ts` (today's fee pace on top; the low end cuts fees to the share of paying half-days, floor one half, and averages each gauge's incentives over the wait, counting every program only until it ends: `incentivePrograms` on each `/api/gauges` row carries the streaming programs' end times, `incentivesOverWait` in `web/lib/gauge-yield.ts` does the average, and the gauge table shows "incentives end in Xh" when at least 5% of them stop inside the wait and marks such a gauge's Steady cell as ending; a program can be renewed, so the pace figure still counts what streams now; checked 2026-10-29 against the chain for RSGP/USDC: incentives $5,314.27 a day vs the app's $5,314.25, fees $41.2k vs $40.7k a day); the per-position staying cost and its total use the same low case (`gainLowUsdPerDay`, `bestLowUsdPerDay` from `analysePosition`) to show a range. A gauge whose fee pace is at least 3x its usual level (the median complete 12 h stretch over the 4-day ledger, `spikeOf` in `web/lib/fee-history.ts`, needs 4+ stretches and a non-empty median) carries `spike` on `/api/gauge-fees`; the table calls its pace "spiky", shows its APR as usual-to-burst, and every low case (`lowFeesUsdPerDay` in `web/lib/projection.ts`) counts its fees at the usual level. Found 2026-10-26 on CHIP/USDC: 21% on our page vs 2.2% on Aero after two releases of $1.9k and $1.5k against a usual ~$400/day. Allocating across chains (`planAcrossChains`, "allocate across chains…" on a position; it plans from where the position is now on EVERY chain, so it also covers partial returns, direct moves between chains and mixed positions): one `allocate()` runs every chain dispatch before every gauge dispatch and a chain dispatch can only draw idle power, so when Base's share goes down the power is first returned to idle with a Base-only call (a DEALLOC entry beside the kept Base gauges; it uses the Base wait), then a second call sends it out and sets each other chain's gauges, never touching Base again (its wait would still run). `msg.value` must equal the sum of the dispatch values, each cross-chain dispatch needs a non-zero gas limit (`CHAIN_STEP_GAS`, `gaugeStepGas(n)`), and the app attaches the adapter quote plus 10% (the rest comes back to the owner: on a fork, net ETH beyond gas equalled the quotes exactly). Verified on an anvil fork of Base as the owner of #15308 on 2026-10-28 (return to idle plus Base gauges, then OP and Arbitrum at 25.5 and 15.3 power, nothing idle). The panel also has "choose the chains myself" (`web/lib/custom-chain-split.ts`): the owner types a percentage per non-Base chain (any of the six, Arc included), Base keeps the rest, and inside each chain the gauges are the best split for its share; also fork-tested leaving Base entirely (lone DEALLOC step, then 40% OP and 60% Arc). The plan is up to two steps: a return step (every chain whose share goes down keeps the gauges it still wants and lists the rest against the DEALLOC marker, all in one call) and a main step (chain dispatches draw idle power for the chains whose share goes up, then their gauges are set); a chain whose amount is unchanged is re-set only if its gauges differ, and differences under about a billionth of the total are treated as rounding (a chain's list must add up to its real budget). Each step carries `chains` (every chain it sets gauges on, each with its own wait), `needsIdle` and `returns`; the panel blocks the next step until each chain's own wait is over, no change is still on its way (the leaf's booked power must match root's amount; checked before the wait, because a chain that has applied a return starts its 47 h wait while Base is not yet credited), and for 15 minutes after a send from this browser. Fees come from `/api/allocation-fee?chain=X&model=1` (chain step, gauge base and per-gauge cost, return cost: a straight line, plus the 10% margin). In "choose the chains myself" the gauges inside a chain can be picked by hand (`parseManualPicks`, shares of the chain adding up to 100%). Fork-tested 2026-10-28 from Base 0 / OP 40% / Arc 60% to Base 30 / OP 20 / Arc 50: step A returned part from OP and Arc, Aero's return messages were played on the fork by calling `processDeallocation` as the orchestrator (a fork can't deliver them), then step B sent 30.6 to Base (Base's own 47 h wait had to be moved past with `evm_increaseTime`). Power already on other chains can also be managed from quick actions in the same panel (`web/lib/allocate-manage.ts`, `web/app/saero-manage-chains.tsx`, `web/lib/leaf-read.ts`): per chain, "set the best gauges" (a full overwrite of that chain's list over its whole budget) or "return to idle" (the whole budget listed against the DEALLOC marker). A dispatch with the marker must carry the chain's `deallocationReturnCost` (the root orchestrator keeps it, `InsufficientDeallocationReturnCost` otherwise) on top of the outbound fee, and the idle power only reappears on Base when the leaf's return message reaches root (`processDeallocation`), minutes later, so a return and a re-send are separate steps; Base itself is instant. The panel reads each chain's own leaf from the browser (all the public nodes allow CORS; dRPC only for our origin), blocks a chain while its own wait runs, while the leaf's booked power doesn't match root's amount (a message still in flight), and for 15 minutes after a send from this browser (`web/lib/pending-lock.ts`), because the transport holds a second message until the wait ends and applies it late. Fork-tested 2026-10-28: both operations accepted, net ETH beyond gas = outbound quote + return cost exactly. A plain gas estimate sat on the out-of-gas edge (the real send reverted once), so the app sends with the estimate plus 30%. A fork can't deliver the leaf-chain messages: the gauge step on another chain arrives later and the transport retries it if that chain's wait is running (`CooldownActive` on the leaf, per Aero's ILeafVoter notes), and until it lands the power shows as idle there. Claiming is `LeafVoter.claimRewards`, callable by the position's operator or the message orchestrator, so it is not built here. The leaf `tokenStates(tokenId)[0]` is the operator; on 2026-10-26 only 3 of 17,591 positions had one.
- **Web UI conventions** (`web/app/ui.tsx`, `globals.css`): buttons, chips and links go through `btn()`, `chip()` and `LINK`, never ad-hoc class strings. Light mode works by mirroring the Tailwind scales (shade 50 <-> 950) under `[data-theme="light"]`, so new colors must come from `neutral`, `sky`, `emerald`, `rose`, `amber` or `violet`; any other family or a hardcoded hex stays dark-themed in light mode. Sky = primary/selected, emerald/rose = positive/negative money only, amber = caution. Tips (`tip-jar.tsx`) are USDC on Base to a fixed public address; the app itself stays free. The product name comes from `DISPLAY_PRESET.appName` ("Aero Allocator"), never `displayName` + "Allocator".
- **Phone layout**: phone-first single page (`saero-page.tsx`) with a sticky jump bar (`jump-bar.tsx`) to Gauges / Positions / Upgrade guide (the guide has no end date: Aero's FAQ says there is no set deadline and its migration contract has no end in its code, so it stays after launch, collapsed once `UPGRADE_CHECKLIST_EXPANDED_UNTIL_MS` has passed); the gauge table shows two columns on a phone with the rest under the pool name. On a phone, once an amount is priced, the gauge section opens with a short card (`web/app/quick-split.tsx`: the best split of up to three gauges, the day's total and its low case, the pace label, "incentives end in Xh", and one button that jumps to the positions panel where the allocation is signed); the long best-split cards, "compare all chains", the flow notes and the whole table are folded behind a "more" button (CSS only, `hidden sm:block`, so from `sm` up nothing changes and the phone card is `sm:hidden`). The table also has a "steadiest only" chip (`isSteadiest` in `web/lib/gauge-yield.ts`: every complete half-day paid, or paid by incentives that run past the wait, and no burst). Phone buttons are at least 44 px tall (`min-h-11`). Keep one wallet button (the header's): `app/page.test.tsx` asserts it.

## Gotchas

- Mobile overflow: a `grid` with no explicit columns sizes its track to its content, so a wide child pushes the whole page sideways on iPhone. Use `grid-cols-[minmax(0,1fr)]` for single-column card grids. Don't make the Pools filter chips scroll sideways; they wrap.
- Checking phone layouts: resizing the browser window does not change the page's CSS width. Load the app in a same-origin `<iframe>` of 360-402px (a temporary `public/*.html` page, with `X-Frame-Options` set to SAMEORIGIN only while testing, then restore DENY and delete the page) and measure with `getBoundingClientRect`. When framing is awkward (components that only render for a connected wallet), copy the component's markup and classes into a temporary page, wrap it in a 360px-wide container and drop the `sm:` classes (a phone has none), then measure `scrollWidth - clientWidth` and clipped labels; the across-chains percent grid overflowed its cells by 49px that way before its labels were stacked above the boxes on phones. The real wallet apps can't be tested in the iOS Simulator; use a real phone.
- Security headers live in `web/next.config.ts` (nosniff, referrer, frame DENY, permissions, HSTS). There is deliberately no CSP yet: wallet dialogs, WalletConnect and the inline theme script need a tuned policy, and a wrong one silently stops wallets connecting.
- Don't add RainbowKit: its latest release (2.2.x) peer-requires wagmi 2 and `web/` is on wagmi 3. The wallet dialog and account panel (`wallet-modal.tsx`, `wallet.tsx`) are built directly on wagmi connectors. The Coinbase and WalletConnect connectors are wrapped by `lazyConnector` (`web/lib/lazy-connector.ts`): wagmi's reconnect asks every connector for its provider on each page load, which used to download and start both SDKs for every visitor (666 KB of JavaScript in 26 files on the live page on 2026-10-30, 356 KB of it wallet code arriving 1.8 s after load; now about 300 KB in 17 files, measured with `performance.getEntriesByType('resource')`), so they load only when the visitor connects with them or when one was the last wallet used (`recentConnectorId`). Import each connector from its own entry point (`wagmi/connectors/walletConnect`, never the `wagmi/connectors` barrel: its Base Account connector drags `@coinbase/cdp-sdk` and a missing `@x402/svm` into the build and the build fails). `@coinbase/wallet-sdk` is only an optional peer of wagmi, so it is a direct dependency of `web/` (added 2026-10-30; until then it was not installed, the Coinbase connector's import failed and the "Coinbase Wallet" button did nothing); it loads only when that button is used (the click loads the connector and the SDK, about 117 KB uncompressed, and Coinbase's own window opens: a script-made click shows its "Popup was blocked" toast, a real tap does not). The WalletConnect connector exists only when `NEXT_PUBLIC_WALLETCONNECT_PROJECT_ID` is set (with a placeholder id its relay socket churns and hangs the tab); on a phone with no injected provider "connect wallet" opens WalletConnect's own wallet window directly (no list): the Coinbase SDK connector only opened the Coinbase app's home screen, and a Coinbase deep-link hop was tried and rejected by the user.
- Paid x402 routes in production: `@x402/next` loads `@x402/extensions/bazaar` with a dynamic import marked `webpackIgnore`, which the bundler and file tracing never see, so the paid functions once shipped without the package and logged "Cannot find package '@x402/extensions'" on every request (caught, harmless, but it buries real errors). `serverExternalPackages: ["@x402/extensions"]` in `web/next.config.ts` makes the build trace it in (check `.next/server/app/api/v1/*/route.js.nft.json`); an `outputFileTracingIncludes` glob into `node_modules` does not work here (Turbopack panics on the `aero-allocator` self-link). A request that carried a payment and still got a 402 is logged as `x402 payment rejected` with the facilitator's reason (`logPaymentRejected` in `web/lib/x402.ts`); read it with `vercel logs --environment production --query "x402 payment rejected" --since 1h --no-follow` (the CLI is installed and the project is linked). Coinbase's facilitator rejects a payment (verify 400, "'paymentPayload' is invalid: must match one of [x402V2PaymentPayload…") when the challenge's resource `description` is over 500 characters (500 passes, 520 does not; found 2026-10-28 when the cross-chain route's 581-character description failed the first paid call), so keep every paid route's `description` at or under 500 (`web/lib/paid-routes.test.ts` enforces it). You can test a payment shape for free: send a route a `PAYMENT-SIGNATURE` header built like the client builds it (the challenge's `resource`, `accepted` and `extensions`) with a fake signature; the facilitator checks the shape first, so a good shape fails only with `invalid_exact_evm_payload_signature` and the logged reason shows which. A paid call that fails with a 402 after signing has not moved any USDC: check for a Transfer to the payout address before assuming it did.
- `web/` uses a Next.js version with breaking changes: read `web/AGENTS.md` (imported by `web/CLAUDE.md`) and the docs in `web/node_modules/next/dist/docs/` before writing web code.
- `.claude/`, `.agents/`, `skills-lock.json` and `.env*` are gitignored, so project skills and `settings.local.json` are local to this machine.
- Aero (the Aerodrome+Velodrome merger) launched 2026-10-22 00:00 UTC. Allocation amounts are voting power (not staked amount); the Voter, sAERO escrow and per-chain leaf voters are in `web/lib/saero.ts` and `web/lib/allocate.ts`. Allocating across chains (`web/lib/allocate-multichain.ts`) handles positions with power on any chain, idle or parked (see the architecture paragraph above). `docs/aero-launch-readiness.md` is the pre-launch research.
